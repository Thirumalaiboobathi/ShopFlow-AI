Who this is for

Intended customer
A single independent electrical or hardware shop in India — typically operating without an ERP, with orders coming through WhatsApp and phone calls, a ledger for customer credit, and a fixed amount of cash available for weekly restocking.
Core workflow
Messy order → verified quote with GST → stock check → supplier price change → margin impact → cash-constrained purchasing → What-If before deciding.
Expected value
Fewer wrong quotations, earlier visibility into supplier price increases, and purchasing decisions based on the cash actually available.
Current validation status
The demo uses synthetic data modeled on an independent electrical-retail workflow. No real shop has used ShopFlow. Real-shop validation is the next step.
What real-shop validation will test
Whether customer messages are matched correctly; how often clarification is required; whether shop owners trust and act on the purchase plan; whether GST treatment matches their existing process; and whether the time saved at the counter is worth paying for.

Supplier prices — read a dealer price list

Photograph a supplier's price list. ShopFlow reads it, matches each line to a catalogue SKU, and compares the printed rate against what this shop last paid. A move of more than 5% is flagged. Reading a supplier price list does not automatically change the shop's cost. Extract → compare → you confirm → the confirmed cost is stored → the planner uses it. Nothing moves until you say so.

The workflow

  1. 1Order A contractor sends a spoken or typed order in everyday shop language. ShopFlow maps it to real catalogue SKUs — and asks when a request is ambiguous instead of guessing.
  2. 2Verify Each line is checked against the shop's current inventory state to find exactly what is short.
  3. 3Quote A clean quotation the owner can read out or share straight away.
  4. 4Supplier intelligence A photographed dealer price list is read and compared against what the shop paid before, surfacing increases that would otherwise pass unnoticed.
  5. 5Protect A confirmed increase is immediately measured against the selling price, so the owner sees what is left of the margin. ShopFlow never changes the selling price by itself.
  6. 6Budget The owner states the cash actually available. That constraint is real, and it binds.
  7. 7Decision A purchase plan: what to buy now, what to defer, and what deferring risks. Customer commitments come first.
  8. 8Why Every recommendation opens up into the full calculation behind it — stock, velocity, lead time, margin, budget remaining.

All eight steps are live above. Every figure comes from the deterministic engine — the language model never writes a number.

The trust principle

The AI never invents business numbers.

The language model understands the order, chooses which tool to call and asks for clarification. Every quantity, price, shortage and total is produced by a separate deterministic engine that cannot reach a model. SKU ids are rejected unless they exist in the catalogue, and any figure the model writes is checked against the engine's output before it is shown. That separation is enforced by the architecture and covered by tests, not asserted in a prompt.

The same line holds for anything consequential. ShopFlow does not change your selling price, does not place an order and does not message anyone. A supplier cost is recorded only when you confirm it, a margin warning is a recommendation you act on yourself, and the WhatsApp buttons open a draft for you to read and send.

Built on

Every service below is deployed in this account, in ap-south-1, and does the job described. Nothing here is aspirational — the stack is one CDK stack you can read in the repository.

Amazon Bedrock

Amazon Nova Pro, called through the Converse API with four strict tools and a bounded loop. It reads the order and asks for clarification. It writes no business number.

Deterministic engine

Pure Python owning matching, inventory, pricing, quotation, margin, credit and budget allocation. Not an AWS service — the point of the architecture.

AWS Lambda

Three functions: the API, the order worker, and a health check.

Amazon SQS + dead-letter queue

Durable hand-off from API to worker. Three attempts, then the message lands in a dead-letter queue a person can open. Worker concurrency is capped at 5 so a burst cannot starve the API.

Amazon DynamoDB

One table: jobs, owner price decisions, and confirmed supplier costs. A conditional write is what makes a duplicate SQS delivery harmless.

Amazon S3

Two private buckets — the site behind CloudFront, and uploads. Voice audio expires after a day.

Amazon CloudFront

Public delivery of the app and the API from one origin, over a private S3 bucket.

Amazon API Gateway

The HTTP API boundary, throttled, in front of the Lambda functions.

Amazon CloudWatch

Logs, metrics, and four alarms: dead-letter depth, sustained worker errors, queue age and agent failures. They alert only — nothing self-heals. CloudWatch alarm actions are configured; notification delivery requires an SNS subscription, and this demo has none.

Amazon Transcribe

Speech to text for spoken orders, in the languages Transcribe actually supports. Quality varies by accent and device.

AWS CDK

The whole stack as Python. One cdk deploy, and a script that refuses any diff removing the budget.

AWS Budgets

A $25/month cost guard with alerts at 50, 80 and 100 per cent.
