# ShopFlow AI

**From messy orders to smarter purchasing decisions.**

An operations assistant for independent electrical and hardware retailers in
India. It turns everyday customer messages and photographed supplier price
lists into verified quotations and cash-constrained purchasing decisions — and
shows the arithmetic behind every one of them.

**Live demo — no login required:** https://d3m3lwn03zb2eu.cloudfront.net

## The problem

A single-shop electrical retailer in India runs on a phone, a paper ledger and
memory. Three things quietly cost them money:

**1. Orders arrive as messy language.** A contractor sends
*"Anna, 2 MCB 32 amp"* — but the shop stocks six different 32A MCBs across
three brands and two pole configurations. Guessing wrong means a callback, a
return, and a customer who goes elsewhere.

**2. Supplier price rises hide in plain sight.** A dealer sends a photographed
price list. Somewhere in it, one wire has gone from ₹5,900 to ₹6,300. Nobody
compares it line by line against what was last paid, so the shop keeps selling
at a margin it no longer earns.

**3. Cash is the real constraint.** The owner has ₹25,000 this week, not
₹250,000. Deciding what to buy is a genuine tradeoff between customer promises
already made and restocking what is about to run out.

## Target customer

Independent electrical and hardware retailers in India — single shop, no ERP,
no POS integration, operating on WhatsApp and a ledger book. The demo is
modelled on Madurai, Tamil Nadu.

## Why this is not a chatbot

A general-purpose assistant will happily produce a quotation total. It will
also, occasionally, produce a *plausible wrong one* — and a shop owner cannot
tell the difference by looking at it. A number that is wrong 3% of the time is
worse than no number at all when someone is about to spend real money on it.

ShopFlow is built the other way around:

> **The language model never writes a business number.**

It understands messy language, picks tools, asks for clarification, and
explains. Every quantity, price, shortage, percentage, total and purchasing
decision is produced by a separate deterministic engine that the model cannot
reach. This is enforced by architecture, not by prompt instructions:

- **The API Lambda has no Bedrock permission at all.** Purchase planning is
  arithmetic over an already-loaded dataset; there is no model on that path to
  invent anything.
- **SKU ids are rejected unless they exist in the catalogue**, so a hallucinated
  product cannot enter the flow even through the front door.
- **Numbers the model writes in its summary are validated** against the
  engine's tool output before the response is returned (`grounded: true`,
  `ungroundedNumbers: []`).
- **Ambiguity is an outcome, not an error.** When several real products match,
  the system asks instead of silently choosing a default.

## Core workflow

```
customer order
  → understand (LLM)
  → SKU match (engine)
  → detect ambiguity → ask the owner       [LLM asks, engine decides it must]
  → inventory check (engine)
  → quotation (engine)

supplier price list photo
  → extract (LLM vision)
  → match to catalogue (engine)
  → price-change detection (engine)
  → OWNER CONFIRMS                          [human gate — nothing moves without it]
  → durable confirmed supplier cost

owner's available cash
  → purchase plan (engine)
  → what to buy, what to defer, and why
```

### What this looks like with real numbers

All figures below are produced by the live system and verified end to end.

**1. A messy order becomes a verified quote**

> *"Anna, 20 Anchor modular switches 1-Way 10A, 3 coils Finolex 1.5 sq mm red
> wire 90m, 2 Havells MCB SP 32A."*

→ **₹22,306.48**, every line checked against live inventory.

**2. An ambiguous order becomes a question**

> *"Anna, 2 MCB 32 amp."*

→ ShopFlow does **not** guess. It asks for the **brand** and offers the six real
32A MCBs the shop actually stocks.

**3. A photographed price list reveals a rise**

→ `W-FIN-1.5-RED-90M`: **₹5,900 → ₹6,300**, a **+6.78%** increase, shown with
its own arithmetic: `(6300.0 - 5900.0) / 5900.0 x 100 = 6.78%`

**4. The owner confirms — and only then does anything change**

→ The confirmed supplier cost is persisted. The **selling price is not touched**
(₹6,608, unchanged). Inventory is not touched.

**5. "I only have ₹25,000."**

| | |
|---|---:|
| Customer commitments (funded first) | **₹12,948.00** |
| Restocking | **₹12,045.16** |
| **Total recommended spend** | **₹24,993.16** |
| **Cash remaining** | **₹6.84** |

**6. The consequence is made explicit**

Confirming that +6.78% rise cost the shop **₹803.40 of restocking capacity** —
the extra ₹800 on two wire coils, plus ₹3.40 as the allocator refits what
remains. A price change buried in a photograph, traced all the way to what the
shop can afford to stock this week.

**7. Every recommendation opens up**

Each deferred item explains itself with engine figures — for example:
stock covers 0.5 weeks at 3.9 units/week, 3-day supplier lead time,
`priority = 0.7875 x 0.35 = 0.275617`.

## Architecture

```
                    ┌──────────────────────────────┐
  Browser  ────────▶│  CloudFront (single origin)   │
  (no login)        └───────┬───────────────┬───────┘
                            │ /api/*        │ everything else
                            ▼               ▼
                 ┌─────────────────┐   ┌──────────────────┐
                 │ API Gateway     │   │ S3 (private,     │
                 │ HTTP API        │   │ OAC only)        │
                 │ 20 rps / 40     │   └──────────────────┘
                 └────────┬────────┘
                          ▼
              ┌───────────────────────┐
              │ API Lambda            │   NO BEDROCK PERMISSION
              │ validate · queue      │
              │ purchase plan (sync)  │
              └───┬───────────────┬───┘
                  │               │ async invoke
                  ▼               ▼
         ┌────────────────┐   ┌──────────────────────┐
         │ DynamoDB       │   │ Worker Lambda        │
         │ single table   │   │ agent loop · vision  │──▶ Bedrock
         │ + GSI1 + TTL   │   └──────────┬───────────┘    (Nova Pro,
         └────────────────┘              │                 one model ARN)
                                          ▼
                                   ┌──────────────┐
                                   │ S3 uploads   │
                                   │ (private)    │
                                   └──────────────┘
```

### The AI / deterministic boundary

| The language model does | The deterministic engine owns |
|---|---|
| Understand messy, abbreviated, mixed-language orders | Inventory and stock levels |
| Choose which tool to call | SKU matching constraints |
| Ask for clarification when a request is ambiguous | Shortages and committed demand |
| Read a photographed price list into structured rows | Quote totals and line arithmetic |
| Summarise and explain in plain language | Supplier price deltas and thresholds |
| | Sales velocity and stock coverage |
| | Stockout risk and margin per rupee |
| | Budget allocation and deferrals |
| | Every number shown to the owner |

The engine (`backend/engine/`, 12 modules) imports no AWS SDK and calls no
model. It runs offline, in a unit test, in milliseconds.

### Request patterns

- **Orders and price lists are asynchronous.** A Bedrock tool loop takes
  seconds; holding a public HTTP connection open that long is a reliability
  risk. The API validates, writes a job record, invokes the worker with
  `InvocationType="Event"` and returns a job id. The browser polls.
- **Purchase planning is synchronous.** It calls no model — measured at
  **3.77 ms** for the full 147-SKU shop. Wrapping that in a job record, an
  async invoke and a polling loop would add three round trips to hide four
  milliseconds of work.

## AWS services

| Service | Use |
|---|---|
| **Amazon CloudFront** | Public entry point; single origin for site and API |
| **Amazon S3** | Static site and uploads — both private, CloudFront via OAC |
| **Amazon API Gateway** (HTTP API) | 7 routes, stage-wide throttling 20 rps / 40 burst |
| **AWS Lambda** | API (512 MB/15 s), worker (1024 MB/60 s), health (256 MB/10 s), Python 3.13 |
| **Amazon DynamoDB** | Single table, PK/SK + GSI1, TTL on job records |
| **Amazon Bedrock** | Amazon Nova Pro — language understanding and document vision |
| **Amazon CloudWatch** | 4 log groups, 14-day retention |
| **AWS Budgets** | $25/month cost guard with 50/80/100% alerts |
| **AWS CloudFormation / CDK** | One stack, Python CDK |

### API routes

| Route | Behaviour |
|---|---|
| `GET /api/health` | Liveness + a real DynamoDB round trip |
| `POST /api/orders` | Validate, queue → `202` + job id |
| `POST /api/supplier-price-lists` | Validate image, queue → `202` + job id |
| `POST /api/price-decisions` | Owner confirms/rejects a detected change |
| `POST /api/purchase-plans` | Deterministic plan → `200` with the plan |
| `GET /api/jobs/{jobId}` | Poll a queued job |
| `GET /api/demo` | Seeded examples, so the UI hard-codes nothing |

An unknown `/api/` route returns a real JSON **404**, while frontend routes
still fall back to the SPA. Getting both behaviours from one CloudFront
distribution required care — see [Engineering lessons](#engineering-lessons).

## Security and least privilege

- **The API Lambda has no Bedrock permission.** Verified against the deployed
  role, not just the template.
- **The worker's Bedrock permission is scoped to one model** — the Nova Pro
  foundation-model ARN and its inference profile. Nothing else.
- **No AWS credentials ever reach the browser.** Price-list images are uploaded
  as base64 through the API; there are no presigned URLs and the uploads bucket
  stays entirely private.
- **Both S3 buckets are private** with public access blocked; CloudFront reaches
  the site bucket through Origin Access Control only.
- **Input is bounded everywhere** — order text 1,000 chars, request body 4 KB,
  images 2.5 MB, 25 items per order, 50 lines per price list, 6 agent turns.
- **Owner-supplied SKU ids are validated against the catalogue** before use.
- **Price comparison figures are read from the stored job**, never from the
  request body, so a caller cannot post numbers the engine never produced.
- **Logs are contents-free.** The worker logs model id, latency, token counts
  and result counts — never order text, product descriptions, supplier names or
  prices. API Gateway access logs carry only requestId, IP, time, route, status
  and latency.
- **Response headers**: HSTS, `X-Content-Type-Options: nosniff`,
  `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`.

## Testing

```bash
python -m pytest            # 336 tests, ~2 seconds, no AWS account needed
```

The engine is pure, so the business rules are tested directly rather than
through HTTP. Coverage includes: velocity and coverage maths, shortage
calculation, SKU matching and ambiguity, quote arithmetic, supplier price
comparison, vision-extraction validation, budget allocation, the purchasing
planner, confirmed-cost persistence, and API request validation.

Guarantees asserted against the real seeded shop at nine budgets from ₹0 to
₹100,000: **total spend never exceeds the budget**, and **remaining cash is
never negative**.

### Real DynamoDB smoke tests

```bash
python scripts/smoke_test_planner.py        # 25 checks against real DynamoDB
```

Deliberately **not** part of the pytest suite — unit tests must stay fast and
runnable with no AWS account. This is run explicitly before a deploy, because
twice the in-memory fake has been wrong in ways no unit test could catch (see
below). It writes only to `SMOKE#`-prefixed keys and deletes them in a
`finally` block.

## Deployment

**Always deploy with `scripts/deploy.sh`. Never call `cdk deploy` directly.**

```bash
export SHOPFLOW_ALERT_EMAIL="you@example.com"   # required
./scripts/deploy.sh                              # diff → review → confirm → deploy
./scripts/deploy.sh --diff-only                  # read-only, no deploy
```

The script exists because the cost budget is created inside
`if alert_email:` — optional CDK context. Synthesising without it silently
produces a template with **no budget**, and deploying that **destroys the cost
guard**. The script therefore:

1. **Refuses to run** without `SHOPFLOW_ALERT_EMAIL` (and sanity-checks it)
2. Always passes `-c alertEmail=… -c monthlyBudgetUsd=25`
3. **Prints the exact command** before running anything
4. Runs `cdk diff` first and shows it
5. **Aborts** if the diff contains `[-] AWS::Budgets::Budget`
6. Lists any other deletions for review
7. Requires interactive confirmation
8. **Verifies after deploying** that `shopflow-monthly` still exists

The email is read from the environment, never committed.

After deploying, follow the verification steps in
[`docs/DEMO-RUNBOOK.md`](docs/DEMO-RUNBOOK.md).

### Demo state

Confirmed supplier costs are durable and shop-wide by design — so a rehearsal
that confirms a price leaves the demo starting mid-story. Reset before demoing:

```bash
python scripts/reset_confirmed_costs.py            # list what would be removed
python scripts/reset_confirmed_costs.py --confirm  # actually remove
```

There is deliberately **no API route or button** for this. Erasing what the
owner agreed to pay is not something a web request should be able to do.

## Coding-agent usage

Built with **Claude Opus 5 via Claude Code**, connected to AWS account
`675613597178` in `ap-south-1` through the AWS CLI using a dedicated IAM user.

The agent did the work directly against AWS rather than generating code for a
human to run:

- Inspected the live environment read-only before changing anything — identity,
  region, bootstrap state, existing stacks — specifically to avoid touching four
  unrelated projects in the same account.
- **Probed Bedrock by actually invoking every candidate model**, rather than
  trusting the model list. This is how Anthropic access being blocked was
  discovered, which set the model choice for the whole project.
- Authored the CDK stack, then **read its own synthesised CloudFormation
  template** before deploying. Two defects were caught at exactly this step,
  including a route-path mismatch that would have made every API call 404.
- Deployed, then **verified against the public URL** rather than assuming
  success — HTTP status, headers, page content, bucket privacy, IAM scope,
  CloudWatch events.
- Diagnosed real failures from CloudWatch logs and CloudFormation events.
- **Recorded its own mistakes** in the development log, including three wrong
  diagnoses and two incorrect test expectations.

Every stage ended with a stop-and-report to a human, who approved before the
next stage began.

## Engineering lessons

Five that changed how the system is built:

**1. A green test suite is not evidence of a working system.**
Twice the in-memory `FakeTable` was wrong in a way no unit test could catch.
First it was too *permissive* — it accepted Python floats where real DynamoDB
rejects them, so every test passed while the deployed endpoint returned 500.
Then it was too *naive* — it could not parse
`Key("PK").eq(...) & Key("SK").begins_with("COST#")`, silently returned nothing,
and **all 336 tests passed while the feature was completely dead**. The second
was caught only by being suspicious of a suite that went green too easily for
the size of the change. Both now have real-DynamoDB smoke coverage, and a test
asserts the fake's own behaviour.

**2. One CloudFront distribution serving both a SPA and an API needs care.**
Mapping 404 to `index.html` for SPA routes also swallowed genuine API 404s,
turning them into 200s with an HTML body. Fixed by mapping only 403 — S3 behind
OAC answers 403 for a missing object, while API Gateway answers 404 for an
unknown route, which separates the two cleanly.

**3. Account limits are shared.** Reserving Lambda concurrency failed because
this account's total concurrency is 10 and AWS requires 10 unreserved. The
reservation was removed rather than risking the starvation of four unrelated
projects in the same account.

**4. A conditional resource is a deletion waiting to happen.** The cost budget
is created inside `if alert_email:`. Deploying without that context would have
silently destroyed it — caught by reading `cdk diff` instead of skipping it.
A prose warning is not a control, so that is now enforced by
`scripts/deploy.sh`.

**5. Consequential state changes need an explicit human boundary.** Detecting a
price rise and applying it are two different things. Extraction never writes a
cost; only an explicit owner confirmation does; a rejection writes nothing; and
a confirmed *supplier cost* never rewrites the *selling price*. Keeping those
separate is most of what makes the system trustworthy.

## Limitations

Stated plainly, because the system is only useful if its claims are reliable.

- **The dataset is synthetic.** 147 SKUs generated at a fixed seed. Not a real
  shop's records.
- **No real users.** No shop has used this. Nothing here is validated against
  real trade.
- **No business-accuracy claim.** The arithmetic is exact and tested; whether
  the *recommendations* are commercially right is unmeasured. There are no
  time-saved, revenue, margin or market-size figures anywhere in this project,
  because none have been measured.
- **Document extraction is tested against one price-list layout**, not arbitrary
  supplier documents.
- **Confirmed costs store only the current value per SKU**, not a history.
- **Ambiguous supplier price-list lines are surfaced but not resolvable in the
  UI** — the owner can see them, not fix them.
- **Clarification is single-round** in the interface.
- **No voice and no Tamil output.** Deliberately not built and not claimed.
- **Single-tenant demo.** No authentication, no multi-shop support.
- **Amazon Nova Pro only.** Anthropic model access is not available on this
  account, so the model adapter defaults to Nova Pro.
